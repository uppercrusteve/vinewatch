# 方法与实现边界

本文记录藤候 VineWatch 的数据口径、编码来源、处理公式、存储结构、导出规则、离线与隐私边界，以及已知局限。应用是田间记录工具，不是物候模型，也不替代正式的 BBCH 培训或检疫鉴定。

## 1. 适用范围

VineWatch 面向单个观察者在无信号葡萄园中的快速记录：先建地块，再按日期与 BBCH 阶段保存记录，可附一张照片、可选坐标和备注。数据全程保存在当前浏览器的 IndexedDB，导出文件由浏览器本地生成。

应用不包含：天气或积温计算、品种参数、地图底图、多用户协作、云端同步、照片 EXIF 解析、面积或产量估算。

## 2. BBCH 编码表与裁剪

### 2.1 来源

主生长期划分与关键码参考：

- Lancashire, P. D., Bleiholder, H., van den Boom, T., Langelüddeke, P., Strauss, R., Weber, E., & Witzenberger, A. (1991). A uniform decimal code for growth stages of crops and weeds. *Annals of Applied Biology*, 119(3), 561–601. <https://doi.org/10.1111/j.1744-7348.1991.tb04895.x>
- Coombe, B. G. (1995). Adoption of a system for identifying grapevine growth stages. *Australian Journal of Grape and Wine Research*, 1(2), 104–110. <https://doi.org/10.1111/j.1755-0238.1995.tb00086.x>

葡萄的扩展 BBCH 使用 7 位编码，主生长期为第 1 位、次生长期为第 2 位。本应用只存两位主码，因为田间口头与表格记录都以主码沟通。

### 2.2 裁剪结果

表中共 8 组 23 码，分组只是界面组织，不改变编码含义：

| 组 | 编码 | 界面短语 | 判定要点（压缩） |
|---|---|---|---|
| 萌芽 | 01 | 芽膨大 | 芽眼膨大、鳞片分离，仍包绒毛 |
| 萌芽 | 07 | 萌芽 | 芽眼绽裂，绿色组织初露 |
| 展叶 | 09 | 展叶 | 第一片叶展开 |
| 展叶 | 13 / 15 / 17 / 19 | 3 / 5 / 7 / 9 叶以上 | 新梢展开叶数，按 2 叶递增 |
| 花序 | 53 | 花序可见 | 花序从叶幕露出 |

| 开花 | 60 | 初花 | 首朵花开放、花帽脱落 |
| 开花 | 65 | 盛花 | 约半数花开放 |

### 2.3 裁剪理由与代价

选择标准是：在田间可快速判别、相邻码能区分、对采样或农事决策有意义。代价是：

- 不含 00（休眠）、02–06、08、10–12、14、16、18、51–52、54–56、58–59、61–64、66–67、70、72、74、76、78、80、82–84、86–88、90、92–96、98–99 等码；
- 不记录次生码（如 65 的第 3 位），不区分主梢与副梢；
- 展叶期以 2 叶为步长，可能错过更细的发育差异；
- 开花期 60/65/68/69 是群体判断，单株边界情况需观察者自行取最接近值。

因此数据适合物候期排序、田块间比较和农事记录，不适合需要完整编码的官方认证。

## 3. GPS 与坐标

坐标来自浏览器 Geolocation API：

```js
navigator.geolocation.getCurrentPosition(success, error, {
  enableHighAccuracy: true,
  timeout: 25000,
  maximumAge: 30000
});
```

- 坐标系为 WGS84（EPSG:4326），与 GeoJSON 要求一致。
- 保存 `lat`、`lon` 与 `accuracy_m`（米）。`accuracy_m` 是浏览器报告的经纬度水平精度半径，按 W3C Geolocation 规范应为 95% 置信水平；保存时四舍五入到整数米。
- 纬度限 -90–90，经度限 -180–180；两者必须同时存在或同时为空。空值存 `null`，不以 0 占位。
- 不采集海拔；地块海拔由用户手工填写（m，0–7000，保留 1 位小数）。
- 列表显示 4 位小数（约 11 m），读取状态显示 5 位小数（约 1.1 m），数据库保留原始浮点值。

没有差分校正、多次定位平均、平滑或轨迹过滤。林冠、坡向、手机硬件与定位服务都会影响结果；在峡谷或密冠下，±20 m 甚至更大的误差很常见。需要米级精度时应使用外部 GNSS 接收机并另行记录。

## 4. 照片压缩

照片在浏览器内处理，原文件不上传、不保存。

1. 输入接受 `image/*`，单文件上限 25 MB（26,214,400 字节），超过即拒绝。
2. 优先用 `createImageBitmap(file)` 解码（应用 EXIF 方向），不可用时退回 `Image` + object URL。
3. 计算缩放：设原图宽高为 `w`、`h`，长边上限 `E = 1280`。若 `w ≤ E` 且 `h ≤ E`，不缩放；否则
   `s = min(E / w, E / h)`，输出
   `w' = max(1, round(w · s))`，`h' = max(1, round(h · s))`。小图不放大。
4. 在 canvas 上以 `imageSmoothingQuality = 'high'` 重绘，调用
   `canvas.toDataURL('image/jpeg', 0.82)`。质量限制在 0.4–0.95 之间。
5. 以 base64 长度估算字节数：
   `bytes = max(0, floor(base64_length · 3 / 4) − padding)`，`padding` 为末尾 `=` 的个数。该值是估算，不是文件系统字节数。
6. 若数据 URL 超过 4,000,000 字符，记录写入时拒绝，提示重新压缩。

后果：**EXIF 全部丢失**（包括拍摄时间、设备与原始 GPS），因此坐标必须由第 3 节的 GPS 按钮单独写入；JPEG 重编码有损，小图也会被重新编码；base64 使存储体积比二进制大约多 33%。每条记录最多一张照片，导入备份时照片随记录一并保存。

## 5. IndexedDB 结构

数据库名 `vinewatch`，版本 `1`，无外部封装库。升级在 `onupgradeneeded` 中建表。

### `plots`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 主键，`plot_<uuid>` |
| `name` | string | 必填，≤ 60 字，去首尾空白 |
| `variety` | string | ≤ 60 字 |
| `elevation_m` | number \| null | 0–7000，1 位小数 |
| `row_note` | string | ≤ 80 字 |
| `created_at` | ISO 8601 string | 创建时间 |

索引：`name`。

### `records`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 主键，`rec_<uuid>` |
| `plot_id` | string | 外键，写入前校验存在 |
| `stage_code` | string | 必须是 23 个已知码之一 |
| `stage_label` | string | 由编码反查的中文短语（冗余） |
| `date` | string | `YYYY-MM-DD`，2000-01-01 至明天 |
| `lat` / `lon` | number \| null | 成对，范围见第 3 节 |
| `accuracy_m` | integer \| null | 米 |
| `photo` | data URL \| null | 用户照片为 `data:image/jpeg;base64,...`；演示集为 SVG data URL |
| `note` | string | ≤ 1200 字 |
| `demo` | boolean | 是否合成演示 |
| `created_at` / `updated_at` | ISO 8601 string | 时间戳 |

索引：`plot_id`、`date`、`stage_code`。

所有写入经过 `normalizeRecord` / `normalizePlot` 校验。删除地块时在同一读写事务内用 `plot_id` 索引游标逐条删除记录，再删地块；任一步失败则整个事务回滚。清空操作清空两个表。首次交互后调用 `navigator.storage.persist()` 尽力申请持久存储，但浏览器仍可驱逐。

## 6. CSV

CSV 由 `toCSV` 生成，共 14 列：记录 ID、地块、品种、海拔(m)、BBCH编码、阶段、日期、纬度、经度、定位精度(m)、备注、演示数据、创建时间、更新时间。

- 文件以 UTF-8 BOM（`U+FEFF`）开头，行尾为 CRLF，末尾也有 CRLF；Excel 因而按 Unicode 打开，中文不乱码。
- 字段含逗号、双引号、CR、LF，或首尾空白时，用双引号包裹；字段内双引号写成两个双引号。
- 空值输出空字段；布尔值输出「是 / 否」；时间戳为 ISO 8601。
- 固定使用逗号分隔与点号小数，不随系统区域设置变化。

CSV 面向 Excel / R / Python 的通用导入，但**未做电子表格公式注入防护**：若备注以 `=`、`+`、`-`、`@` 开头，Excel 可能按公式解释。照片不进入 CSV。

应用内导出时会在序列化结果前再补一个 BOM 并去掉原 BOM，避免重复；测试直接校验 `toCSV` 的首字符为 `U+FEFF`。

## 7. GeoJSON

- 输出 RFC 7946 `FeatureCollection`，每个要素为 `Point`，坐标顺序 `[经度, 纬度]`，小数位不截断。
- 只包含 `lat`、`lon` 均为有限数值且在范围内的记录；无坐标、单边坐标、字符串坐标与越界坐标全部跳过。
- `properties` 含记录 ID、地块 ID、地块名、品种、海拔、BBCH 编码与短语、日期、定位精度、备注、演示标记。
- 不含 `crs` 成员（RFC 7946 默认 WGS84）；不含照片，照片只在 JSON 备份中。
- 没有坐标的记录仍会出现在 CSV 与 JSON 中。

没有坐标的记录通常来自峡谷遮挡、权限拒绝或观察者主动留空；导出时会提示「没有带坐标的记录」，而不是生成空图层。

## 8. 离线与隐私边界

### 离线

- Service Worker 只处理同源 GET。导航请求走网络优先、失败回退缓存的 `index.html`；静态资源走缓存优先。跨源请求不拦截。
- 安装时预缓存 `index.html`、样式、清单、图标、脚本与应用入口；单个资源失败不阻断安装（`Promise.allSettled`）。
- 缓存版本为 `vinewatch-v1`，激活时删除其他版本。**发版必须改版本号**，否则旧缓存可能长期滞留。
- Service Worker 仅在 `http:` / `https:` 下注册，`file://` 打开没有离线缓存。
- 记录写入只依赖本地 IndexedDB，断网不影响新增、编辑、筛选或导出。
- 浏览器可能驱逐站点数据；iOS 的存储策略更保守。定期导出 JSON 是唯一可靠的备份手段。

### 隐私

- 无账号、无后端、无云同步、无分析脚本、无外部字体或 CDN。在线时 GitHub Pages 只看到常规静态资源请求。
- 记录、照片与坐标写入当前源的 IndexedDB；不同浏览器、浏览器配置文件、协议或主机名互相隔离。`http://127.0.0.1` 与 `https://uppercrusteve.github.io` 的数据不互通。
- 定位本身可能由操作系统或浏览器的网络定位服务提供，因而不保证纯离线；照片、导出与存储全部本地。
- JSON 备份**不加密**，含精确坐标、照片与备注。分享前应自行检查敏感地块信息。
- 清理站点数据、卸载 PWA 并清除数据、或使用隐私窗口，都会使应用内数据不可恢复；隐私窗口的数据在窗口关闭后删除。

## 9. 日期、排序与统计

- 日期是本地日历日，不含时间与时区；允许到「明天」是为跨时区与设备时钟误差留缓冲。
- 输入用 UTC 构造探针校验日历真实性，因此 `2023-02-29` 会被拒绝。
- 列表按日期降序、同日按 `created_at` 降序；导出按日期升序。
- 搜索匹配地块名、品种、阶段短语/编码、备注与日期，忽略大小写；列表先渲染最近 200 条，超出时显示「加载更多」与总数，统计与导出不受此限制。
- 「今日记录」按设备本地日期计数；「最近阶段」取日期最大的有效记录，同日多阶段时取创建较晚者，不代表全园真实最大物候。

## 10. JSON 备份与导入

备份信封为 `{schema: "vinewatch-export", version: 1, app, exported_at, counts, plots, records}`。导入流程：

1. 解析 JSON，校验对象与 `schema`；
2. 逐行校验地块与记录，收集失败原因（最多展示 50 条）；
3. 记录按 ID 与指纹
   `plot_id | stage_code | date | lat | lon | accuracy_m | photo_digest | trim(note)`
   去重，已有 ID 或相同指纹则跳过；`photo_digest` 由照片长度与首尾片段构成，
   照片不同或定位精度不同的记录会分别保留；
4. 只在同一事务内写入通过校验的行，只合并不覆盖。

指纹不包含品种、海拔与时间戳，因此只有地块、阶段、日期、坐标、精度、照片与备注全部相同的两条记录才会被视为重复。导入器信任 `schema` 标记，不做密码学完整性校验，也不限制文件大小。

## 11. 已知局限

1. BBCH 是裁剪表（23/100 主码），无次生码、无主副梢区分，不能用于官方物候认证。
2. 无地图与就地纠偏；坐标只能查看文本，不能在地图上拖拽修正。
3. GPS 精度取决于设备与环境，无 averaging、无差分、无外部 GNSS 接入。
4. 照片有损、EXIF 丢失、每条一张；照片直接存 base64，占空间且拖慢大列表。
5. 单设备单用户；无冲突解决、无同步、无审计日志，编辑覆盖旧值且不保留修订历史。
6. 存储可能被浏览器驱逐；无自动备份、无加密备份、无导出提醒。
7. CSV 对以 `= + @ -` 开头的文本加前导单引号防公式注入，导入 Excel 后会显示该引号；日期无时间与时区；备注换行会让部分简易解析器误判行数。
8. 导入去重依赖内容指纹，完全相同的两条记录无法区分是否有意重复；导入无大小上限与进度条。
9. 搜索为内存过滤，记录数大时变慢；列表每次加载 200 条，靠「加载更多」扩展。
10. 未做端到端浏览器自动化；`app.js` 的 DOM 接线由手工验收，单元测试覆盖纯逻辑与数据层。截图脚本依赖本机 Playwright，本仓库不含其依赖。
11. HEIC/HEIF 能否解码取决于浏览器；不能解码时给出单独的格式提示，要求先导出为 JPEG。
12. Service Worker 缓存优先；缓存名由构建哈希决定，每次构建自动更换并清理旧缓存。
13. 只在 Chromium 与 WebKit 的常规能力上设计，未逐一验证所有浏览器版本。
14. 演示集的坐标与记录均为合成，不能作为德钦任何地块的实测依据。
